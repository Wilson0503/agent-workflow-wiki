1. AI Agent 概念升級與工具選用策略
1.1 Agent 的核心公式與 Harness 設計
在現代生成式 AI 架構中，AI Agent 的本質並非單純的單向對話視窗，其核心構造可精確歸納為以下關係：
AI Agent = AI Model + Harness
AI Model（模型）：具備理解與生成語言能力的基礎大語言模型（LLM）。
Harness（控制與規範架構）：專指「告訴 AI 如何按步驟做事的機制、規範與工作流程」。Harness 的設計品質直接決定了 Agent 能否穩健執行多階段、複雜的實務任務。
學習並掌握這些業界專有名詞（如 Harness、LOP、Graph）的目的，在於建立明確的技術認知——出外不被話術欺騙，必要時能精準理解並掌控 AI 工作流程的設計語法。
在提問與上下文處理的演進上，技術發展分為兩個層次：
Prompt Engineering（提示工程）：聚焦於如何設計提問指令，以及透過與 AI 進行多輪反覆討論、互動修正來提煉最佳產出的技巧。
Context Engineering（上下文工程）：聚焦於如何構建並傳遞「足夠充分且正確的背景資訊」給 AI。常見應用包括傳統的 RAG（檢索增強生成）以及本課程重點實作的 LM Wiki，核心目的均為避免 AI 在資訊不足的情況下盲目猜測或產生幻覺。
1.2 Work Agent 與 Coding Agent 之比較
目前市場上的 AI 工具已分化出「Work Agent」與「Coding Agent」兩大實務導向。雖然 Coding Agent 名稱包含 "Coding"，但其本質並非僅限於編寫程式碼，而是模仿人類操作電腦專案資料夾、存取硬碟檔案與管理工作流程的行為模式。

1.3 本地端資料夾管理與工具選用邏輯
使 AI 直接連動並管理電腦本地端的「專案資料夾」具備極高的實務價值。人類日常在電腦上整理報告、存取資料均基於硬碟目錄結構；當 AI 能夠存取本地資料夾時，方能真正融入人類既有的工作習慣。
在工具選用上，課程以 Google AntiGravity 作為主要示範平台，核心理由在於 Google 提供學生方案（優惠付費存取權），讓學生能以較低門檻取得高品質模型存取權。同時，專案邏輯保持彈性，使用者亦可選用 Claude Code 或 ChatGPT Codex 來完成相同的任務。
在操作心法上，Coding Agent 雖然提供許多預設指令，但指令實質上僅為快捷鍵（Shortcut）。使用者無需背誦繁瑣指令，直接透過自然的口語表達（「出一張嘴」下達需求），AI 即可自動轉化為對應的專案檔案操作。

2. Agent 控制流程拆解：Loop（迴圈）與 Graph（圖形）架構
2.1 LOP（Reflection Loop / 反思迴圈）架構解析
Reflection Loop（LOP）的核心機制是透過多個 Agent 角色的分工與反覆交互，達到自動化品質提升。正如業界先進所言，當前設計 Agent 時已不再僅寫單次 Prompt，而是著重於設計 Prompt Loop。
LOP 運作步驟：
作者 Agent（Author）：依據需求生成初始版本的內容。
審查員 Agent（Reviewer）：依據既定品質標準審查該內容，列出缺點與具體修正建議。
反饋修正：作者 Agent 接收審查報告進行修訂，生成新版本並再次送交審查員。
LOP 架構成功的關鍵要素：
客觀的放行條件：必須明確定義「品質達到何種程度才算合格」，使審查員能在符合標準時放行結束。
強迫煞車機制（停損點）：避免 AI 進入無窮迴圈或消耗過多 Token 成本，必須設定明確的停止條件：
最大次數限制：設定強制停止上限（如最多反覆修訂 3 至 5 次）。
資訊不足即停：審查發現缺乏關鍵原始資料時自動中斷迴圈，提示人類補充資訊。
成本與效益控管：防止無效的重複修訂導致 Token 費用浪費。
2.2 Grave（Graph / 圖形）架構解析
相較於固定的 Loop 迴圈，Graph（圖形架構，簡稱 Grave）具備更高度的動態彈性。Graph 允許工作流在不同的「節點（Node）」之間，依據特定條件自由跳躍與回溯。
Graph 運作機制與節點定義：
單一節點（Node）任務專一化：每一個 Node 專注於執行特定的獨立任務。例如：Node A 負責撰寫文章大綱、Node B 負責檢查邏輯漏洞與邊界條件、Node C 負責輸出最終評估報告。
動態條件跳躍：流程執行並非線性發展。若在 Node C（輸出報告階段）發現原始資料有遺漏，系統可依條件控制動態跳回 Node B（審查階段），甚至回退至 Node A（大綱重置階段），待補齊條件後再重新推進。
2.3 流程設計的實務心法
專案設計者切忌盲目追求複雜的 Loop 或 Graph 工程。優質的 Agent 流程應當從人類實際處理業務的自然步驟中演化而來：
簡單提示工程（Prompt Engineering）能一次解決的問題，絕不調用 Loop。
標準 LOP 能解決的問題，絕不盲目過度工程化（Over-engineering）去堆疊複雜的 Graph 節點。

3. 基於 LM Wiki 的知識庫建置實務（Karpathy 模式）
3.1 LM Wiki 與 RAG 的技術對照
LM Wiki 概念源自 Andrej Karpathy 的實務倡議。Karpathy 最初亦試圖建置傳統 RAG（檢索增強生成），但隨後發現只需將資料結構化切碎為 Markdown 檔案，直接置入大語言模型的上下文（Context）窗口中，即可達成極佳的檢索與理解效果。
知識碎片化：將龐大文獻切碎為小區塊（Markdown 格式的獨立頁面與知識碎片）。
AI 導向檢索：LM Wiki 的內容主要供 AI 在 Context 窗口內進行檢索與精準提取，而非供人類線性閱讀。
免除繁瑣管線：無需轉化向量與建立複雜的檢索管線，直接透過結構化的 Markdown 檔案目錄，讓 Agent 在上下文範圍內實現精準擷取。
3.2 需求訪談與 agent.md 專案憲法構建
在建置 LM Wiki 前，AI 必須扮演訪談者，向使用者釐清以下關鍵變數：
研究廣度與深度：屬於狹窄領域的深入探討，或是跨領域的廣泛知識整理。
來源資料格式：原始輸入為 PDF 論文檔、arXiv 網址連結或圖片素材。
筆記連結風格：採用雙向連結（Wikilinks）語法與相對路徑規範。
語言與公式保留：設定內文主語言（如繁體中文）以及專業術語、LaTeX 數學公式的保留規則。
訪談結束後，AI 會自動生成 agent.md（或 gemini.md）。該檔案為專案憲法與員工作業手冊，嚴格規範專案目錄結構：
project-root/
agent.md（或 gemini.md）：專案憲法與 Agent 行為規範手冊
papers/：存放原始論文 PDF 與輸入資料檔
wiki/：AI 自動生成與維護的 Markdown 知識碎片頁面
assets/：存放簡報圖片、標籤與視覺素材
3.3 論文導入與 Obsidian 關聯圖譜可視化
當使用者將學術論文（例如：LLM 在教育領域之應用）輸入 Agent 後，Agent 將依照 agent.md 規範執行自動化處理：
解析論文內文，將原始檔存入 papers/。
在 wiki/ 目錄中生成單頁摘要、提取核心概念頁與方法論碎片，並自動建立 Markdown 雙向連結。
Obsidian 圖譜可視化：當使用 Obsidian 筆記軟體開啟該 Wiki 資料夾時，點擊「關聯圖（Graph View）」，系統會自動將零碎 Markdown 的雙向連結渲染為網絡圖譜。這能使知識庫結構極具專業感與視覺吸引力。

4. 實戰演練：運用 Graph 流程將 LM Wiki 轉化為 HTML 簡報
4.1 簡報視覺風格與需求定義
在將 LM Wiki 知識庫輸出為展示簡報前，Agent 會先進行風格與視覺需求釐清：
風格設定：定義簡報視覺風格（例如：「日系可愛粉采風」）。
素材綁定：指定圖片素材路徑綁定至 assets/ 資料夾，並校正相對路徑語法。
版面定位：確認產出為「圖文講義型」（供個人學習/細讀）或「演講演示型」（供課堂展示）。
4.2 Graph 多階段簡報生成流程拆解
為避免單次生成導致內容偏頗或無效網頁，系統採用 Graph 架構將簡報製作拆解為四個核心節點與檢查機制：
Node 1：大綱研擬節點 (Outline Node)
任務：從 LM Wiki 中擷取主題資訊，擬定詳細簡報大綱。
人類最佳檢查點 (Human Checkpoint)：大綱生成後，人類管理者在此關卡審核內容邏輯與涵蓋範圍。在大綱階段進行修正能避免後續 HTML 網頁重做的巨大成本。
Node 2：逐頁內容生成節點 (Page Content Node)
任務：基於已確認的大綱，細化每一頁簡報的具體文字文案、圖表置放位置與文獻引用。
Node 3：HTML/CSS 渲染節點 (HTML Rendering Node)
任務：載入指定視覺風格（如日系粉采風 CSS），將逐頁內容編譯為單頁或多頁整合型 HTML 網頁簡報。
Node 4：自動驗證與審查節點 (Validation Node)
任務：自動檢視產出的 HTML 網頁，檢查圖片路徑（assets/ 連結）是否斷連結、引用文獻是否精準、版面文字是否溢出。若驗證未通過，動態跳回 Node 2 或 Node 1 進行修正。
4.3 版本控制與成果交付
在 Coding Agent 工作流中，深度結合 Git 進行本地版本控管（執行 git init）具有顯著優勢：
Git（本地控管）與 GitHub（雲端平台）之差異：Git 是在使用者電腦本地端進行專案歷程追蹤與版本復原；GitHub 則是將本地專案推送到雲端託管的網頁平台。
歷程復原：若 AI 在進行多輪 HTML 渲染時搞砸檔案格式，管理者可隨時透過 Git 復原至先前的良好狀態。
這套架構完整體現了現代管理者/老闆的 AI 協作思維： 管理者無須親自撰寫 HTML/CSS 或手動調整版面排版，只需「出一張嘴」給予方向，精準掌控「大綱審核」與「最終檢查報告」兩個核心關卡，中間重複性的檔案生成、驗證與修改，均交由 Agent 自動化執行。
4.4 AI 檢視重點與核對題目
