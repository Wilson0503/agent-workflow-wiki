概念

基礎

  • AI 代理（AI Agent） — 多步驟自主執行、會用工具的 AI，Model + Harness
  • 控制工程（Harness Engineering） — 告訴 AI 怎麼按步驟做事的規範與流程
  • 提示工程（Prompt Engineering） — 設計怎麼問、多輪修正
  • 上下文工程（Context Engineering） — 給 AI 足夠且正確的背景資料，避免幻覺
  • 檢索增強生成（RAG） — 先檢索段落再回答；知識不累積、像黑盒子
  • LLM 知識庫（LLM Wiki） — LLM 維護的互連 Markdown 知識庫

三種做事方法

  • 反思（Reflection） — 先產生、再檢查、再修改
  • 工具使用（Tool Use） — 依需求選擇並呼叫工具
  • 規劃（Planning） — 先拆步驟、打草稿再執行

流程控制

  • 反思迴圈（Reflection Loop） — 作者 ⇄ 審查員反覆修訂
  • 圖形工作流（Graph） — 節點＋條件跳躍的流程
  • 煞車機制（Stopping Conditions） — 次數上限、資訊不足即停、成本控管
  • 人類檢查點（Human Checkpoint） — 大綱階段是人類最佳檢查點
  • Token 成本（Token Cost） — 多階段呼叫讓用量倍增
  • 過度工程化（Over-engineering） — Prompt → Loop → Graph，能簡單就簡單

專案化

  • 員工手冊（AGENTS.md / CLAUDE.md） — 員工手冊：成果、約束、驗收、先計畫
  • 技能包（Agent Skills） — 把好流程打包成可重用 SOP
  • Coding Agent 與 Work Agent — 對話視窗 vs 操作專案資料夾
  • Git 版本控管（Git Version Control） — 本機版本控管，AI 改壞可復原

  • s4 的「Graphite Engineering」疑為轉錄錯誤，未收錄，需人類確認原意。

主題總覽：AI Agent 怎麼做事？

更新：2026-11-23 ｜ Markdown 原檔

一頁讀懂整個 wiki：Agent = Model + Harness，而 Harness 的核心是「怎麼安排步驟、怎麼檢查」。

一條主線

  1. Agent 是什麼：AI 代理（AI Agent） = Model + 控制工程（Harness Engineering）。和對話型 AI 的差別是多步驟自主執行、會用工具、能操作檔案（s4、s6）。
  2. 給它對的資訊：提示工程（Prompt Engineering） 管「怎麼問」，上下文工程（Context Engineering） 管「給什麼資料」；做法有 檢索增強生成（RAG） 與 LLM 知識庫（LLM Wiki）（s1、s5、s6）。
  3. 三種基本做事方法：反思（Reflection）、工具使用（Tool Use）、規劃（Planning）（s3、s2）。
  4. 把步驟串成流程：固定來回的 反思迴圈（Reflection Loop），與可依條件跳躍的 圖形工作流（Graph）（s6）。
  5. 讓流程可控：煞車機制（Stopping Conditions） 防止無窮迴圈、Token 成本（Token Cost） 提醒每一步都要錢、人類檢查點（Human Checkpoint） 讓人在最划算的時機介入（s2、s6）。
  6. 別做過頭：過度工程化（Over-engineering）——Prompt → Loop → Graph，一層不夠才往下一層（s6）。
  7. 寫成規則、留下版本：員工手冊（AGENTS.md / CLAUDE.md）、技能包（Agent Skills）、Coding Agent 與 Work Agent、Git 版本控管（Git Version Control）（s4、s5、s6）。

  • 第七週 RAG 作業範例講解、第八週 Agent 實作示範講解（07C Planning）、第八週作業：用程式做一個簡單的 AI Agent、第九週課程大綱：Agent 原理、Harness 與專案構建、Karpathy — LLM Wiki（idea file）、第十週課程：工作流程拆解與 Agent 架構（Loop 與 Graph）

第七週 RAG 作業範例講解

原始檔：raw/s1_w07_RAG範例講解.txt ｜ 更新：2026-11-23 ｜ Markdown 原檔

這份資料在講什麼

課程影片 1:22:02～1:49:50 的整理：老師用「勞動部工讀生權益」示範資料集，講解兩支 Colab 程式——R01 建立並匯出向量資料庫、R02 載入向量庫做 RAG 對話機器人並用 Gradio 展示，以及作業哪些地方不能照抄。

重點摘錄

  • 資料集先切成一塊塊 .txt，每塊有標題、Metadata、要做 Embedding 的內文、練習檢索問題。
  • R01：安裝 sentence-transformers 與 FAISS → 載入 Embedding 模型 → 內文轉向量 → 打包前先用測試問題驗證檢索結果 → 匯出 zip。
  • R02：用 API 呼叫 LLM（範例用 Groq）→ 載入向量庫 → System Prompt＋User Prompt 把檢索到的資料和問題結合，讓 LLM 像做「閱讀測驗」一樣回答。
  • 測試時要確認機器人「嚴格根據資料回答，而不是自行幻想（Hallucination）」。
  • 找不到資料時的回應要改成符合情境的句子（例如「本資料庫中查無相關規定」）。
  • R02 必須自動下載向量庫，助教按「全部執行」就能跑。

產生／更新的概念

  • 檢索增強生成（RAG） — RAG 的完整流程與「先驗證檢索再打包」
  • 上下文工程（Context Engineering） — 把檢索到的背景資料放進 Prompt，避免幻覺
  • 提示工程（Prompt Engineering） — System Prompt / User Prompt 的分工、找不到資料時的回應

第八週 Agent 實作示範講解（07C Planning）

原始檔：raw/s2_w08_Agent實作講解.txt ｜ 更新：2026-11-23 ｜ Markdown 原檔

這份資料在講什麼

第八週課堂後半段的整理：三個範例 07A Reflection、07B Tool Use（飲料店）、07C Planning（將倒楣事正向轉化的思考生成器），以及老師口頭補充的實務陷阱。

重點摘錄

  • 07A＝Reflection、07B＝Tool Use（飲料店範例）、07C＝Planning；不熟程式的同學老師推薦 07C。
  • Agent 很燒 Token：一般問答呼叫一次模型，Agent 是多階段架構（先規劃／打草稿，再正式生成），每階段都呼叫模型，Token 消耗倍數成長。
  • Groq 免費 API 容易跑到一半因額度中斷；改用較小模型可降低中斷機率；商業應用要用付費 API。
  • 範例程式寫滿預設為 False 的測試開關，避免一執行就燒光額度。
  • AI 幫忙寫的 Prompt 常常太長，有些模型吃不下，反而變差，要親自測試並精簡。
  • 「AI 思考」的本質是打草稿，打草稿的步驟是人類用 System Prompt 教它的（先確認事實 → 評估失落點 → 發想幽默切入點 → 最後生成正文）。

產生／更新的概念

  • 規劃（Planning） — 07C：先打草稿再生成；思考＝打草稿
  • Token 成本（Token Cost） — 多階段呼叫讓 Token 倍增、免費 API 限制、測試開關
  • 提示工程（Prompt Engineering） — AI 寫的長 Prompt 陷阱
  • 工具使用（Tool Use） — 07B 飲料店範例
  • 反思（Reflection） — 07A 為 Reflection 範例
  • 煞車機制（Stopping Conditions） — 預設 False 的測試開關是程式層的防呆

第八週作業說明：從 Reflection、Tool Use、Planning 三種方法選一種，參考 Demo07a/b/c 改成自己的 Agent，並用 Gradio 展示。

重點摘錄

  • Reflection：讓 AI 先產生結果，再自行檢查、反思並修改答案。
  • Tool Use：讓 AI 根據需求選擇並使用工具，例如計算機、搜尋功能、自己寫的 function。
  • Planning：讓 AI 面對任務時先拆解步驟，再依照計畫逐步完成。
  • 重點不是做很複雜的系統，而是理解所選方法並讓它在程式中實際運作。
  • 高分條件之一：方法要「明確呈現在程式流程中」，執行結果看得出 Agent 依設計處理，並有進一步調整、測試或改良。

產生／更新的概念

  • 反思（Reflection） — 先產生、再檢查、再修改的定義
  • 工具使用（Tool Use） — 選擇並使用工具的定義與工具例子
  • 規劃（Planning） — 先拆解步驟再執行的定義
  • AI 代理（AI Agent） — Agent 的三種基本做事方法
  • 過度工程化（Over-engineering） — 「重點不是非常複雜的系統」

第九週課程大綱：Agent 原理、Harness 與專案構建

原始檔：raw/s4_w09_Harness與AGENTS課程大綱.txt ｜ 更新：2026-11-23 ｜ Markdown 原檔

這份資料在講什麼

第九週簡報文件整理：從「對話型 LLM」到「代理型 AI Agent」的範式轉移、Harness Engineering、專案資料夾與 agent.md / claude.md 員工手冊、Skill 打包、工具比較、三個實務案例，以及 SIMA 研究與神經網路訓練的複習（後兩者與本主題無關，未收錄）。

重點摘錄

  • 使用者角色從手動整理資料的「打工仔」，變成只下達目標與驗收標準的「管理者／老闆（出一張嘴）」。
  • 對話型 AI：一問一答、全程需人工在場、只在對話框內生成文字。Agent：多步驟自主執行、交代任務後可離場、可讀寫本機檔案、調用工具，產出完整專案成果。
  • AI Agent = AI Model（LLM 大腦）+ Harness；頂級模型基礎實力差距縮小，決定優劣的是 Harness（引導 AI 做事的方法、檢查機制、工具介面）。Harness 涵蓋 Prompt、RAG、機制的設計。
  • 員工手冊 agent.md / claude.md / gemini.md：寫清楚成果定義、約束條件、驗收標準、先計畫後執行。
  • 做出滿意的流程後，可請 AI 把 SOP 打包成 Skill，之後反覆調用，品質與風格不會隨機波動。
  • 案例「桌面檔案分類器」：Agent 先擬 5 類分類計畫 → 管理員確認 → 才建資料夾、搬檔案 → 回報結果。
  • LLM Wiki 比向量 RAG 更可解釋：人和 LLM 都能直接讀 index.md 與條目，「找對找錯一目瞭然」。
  • 簡報要求：首頁 index.html 集中連結所有簡報；GitHub 要上傳完整專案（規則檔、assets、中間產物），評分看規則檔與專案引導結構。

產生／更新的概念

  • AI 代理（AI Agent） — 對話型 AI 與 Agent 的比較
  • 控制工程（Harness Engineering） — Agent = Model + Harness
  • 員工手冊（AGENTS.md / CLAUDE.md） — 員工手冊的四個要素
  • 技能包（Agent Skills） — 把 SOP 打包成 Skill
  • 人類檢查點（Human Checkpoint） — 先計畫後執行、管理員確認
  • LLM 知識庫（LLM Wiki） — 可解釋性、index.md
  • 檢索增強生成（RAG） — 向量 RAG 的黑盒子缺點
  • 工具使用（Tool Use） — Agent 調用工具
  • 規劃（Planning） — 先計畫後執行
  • Coding Agent 與 Work Agent — OpenWorker + Ollama 本地方案

Karpathy — LLM Wiki（idea file）

原始檔：raw/s5_w09_Karpathy_LLM_Wiki.txt ｜ 更新：2026-11-23 ｜ Markdown 原檔

這份資料在講什麼

Andrej Karpathy 的 gist（英文原文）：一種讓 LLM 持續建立、維護個人知識庫的模式，以及它和 RAG 的差別、三層架構、三種操作、index / log 兩個特殊檔案。

重點摘錄

  • RAG 每次提問都從原始文件「重新發現」知識，沒有累積；LLM Wiki 是 LLM 逐步建立並維護的持久 wiki，知識編譯一次、持續更新。
  • 三層：raw sources（不可修改，事實來源）→ wiki（LLM 全權撰寫維護）→ schema（CLAUDE.md / AGENTS.md，規定結構、慣例與流程）。
  • schema 讓 LLM 成為「有紀律的 wiki 維護者，而不是一般聊天機器人」，由人和 LLM 一起持續調整。
  • 三種操作：Ingest（讀來源、討論重點、寫摘要、更新相關頁、記 log）、Query（讀 index 找頁面、附引用回答，好答案可存回 wiki）、Lint（找矛盾、過時說法、孤兒頁、缺頁）。
  • index.md 是內容目錄；log.md 是只追加的時間序紀錄，用固定前綴 ## [日期] ingest | 標題 方便 grep。
  • 中等規模（約 100 份來源）只靠 index 檔就夠，不需要 embedding RAG。
  • 人負責挑資料、引導分析、問好問題；LLM 負責摘要、交叉引用、歸檔等雜務。wiki 就是一個 git repo，有版本歷史。

產生／更新的概念

  • LLM 知識庫（LLM Wiki） — 三層架構、三種操作
  • 檢索增強生成（RAG） — RAG 沒有累積
  • 員工手冊（AGENTS.md / CLAUDE.md） — schema 檔的角色
  • 人類檢查點（Human Checkpoint） — 作者偏好一次 ingest 一份並親自檢查
  • Git 版本控管（Git Version Control） — wiki 就是 git repo

第十週課程：工作流程拆解與 Agent 架構（Loop 與 Graph）

原始檔：raw/s6_w10_Loop與Graph課程說明.txt ｜ 更新：2026-11-23 ｜ Markdown 原檔

這份資料在講什麼

第十週 1:52:00 課程精華整理：Agent = Model + Harness、Prompt / Context Engineering、Work Agent 與 Coding Agent、Reflection Loop 與 Graph 架構、LLM Wiki 建置，以及用 Graph 把 LLM Wiki 轉成 HTML 簡報的四節點流程。

重點摘錄

  • Harness＝「告訴 AI 如何按步驟做事的機制、規範與工作流程」，品質決定 Agent 能否穩健完成多階段任務。學名詞是為了「出外不被話術欺騙」。
  • Prompt Engineering：設計提問、多輪討論修正。Context Engineering：給 AI 足夠且正確的背景資訊（RAG、LLM Wiki），避免它在資訊不足時亂猜或幻覺。
  • Coding Agent 不只寫程式，本質是「模仿人類操作電腦專案資料夾」；指令只是快捷鍵，直接用口語交代即可。
  • Reflection Loop：作者 Agent 產生 → 審查員 Agent 依標準列缺點與建議 → 作者修訂再送審。成功關鍵：客觀放行條件＋煞車機制（最多 3～5 次、資訊不足即停、控管 Token 成本）。
  • Graph：每個 Node 專注一件事，流程可依條件在節點間跳躍、回溯（例如在輸出報告階段發現資料遺漏，就跳回審查或大綱節點）。
  • 設計心法：簡單 Prompt 能解決就不用 Loop；Loop 能解決就不要過度工程化堆 Graph。流程應從人類實際做事的步驟演化而來。
  • LLM Wiki 建置前 AI 要先訪談（廣度深度、來源格式、連結風格、語言與公式規則），再產生 agent.md 專案憲法。Obsidian Graph View 可把雙向連結畫成網絡圖。
  • 簡報 Graph：Node 1 大綱（人類最佳檢查點，在這裡修正可避免重做 HTML）→ Node 2 逐頁內容 → Node 3 HTML/CSS 渲染 → Node 4 自動驗證（圖片路徑、引用、文字溢出），不通過就跳回 Node 2 或 Node 1。
  • Git 是本機版本控管、GitHub 是雲端平台；AI 搞砸檔案時可用 Git 復原。

產生／更新的概念

  • 控制工程（Harness Engineering）、提示工程（Prompt Engineering）、上下文工程（Context Engineering）
  • Coding Agent 與 Work Agent

AI 代理（AI Agent）

來源：s3、s4、s6 ｜ 更新：2026-11-23 ｜ Markdown 原檔

會自己多步驟做事、用工具、讀寫檔案的 AI：Model + Harness。

重點

  • 公式：AI Agent = AI Model + Harness；Model 負責理解與生成語言，Harness 負責「怎麼按步驟做事」（s6、s4）。
  • 和對話型 AI 的差別：對話型是一問一答、全程要人在場；Agent 是多步驟自主執行，交代完可以離場（s4）。
  • Agent 能讀寫本機檔案、建資料夾、開瀏覽器、調用工具，產出的是完整專案成果，而不只是一段回答（s4）。
  • 人的角色從「打工仔」變成「管理者／老闆」：只要下達目標與驗收標準（s4）。
  • 三種基本做事方法：Reflection、Tool Use、Planning（s3）。

例子

  • 桌面檔案分類器：Agent 讀目錄、擬分類計畫、等確認後自己搬檔案並回報（s4）。

常見誤區

  • 以為 Agent 是「更聰明的聊天視窗」。差別不在模型，而在 Harness 讓它能多步驟執行、操作檔案和工具（s4、s6）。

相關概念

  • 控制工程（Harness Engineering） — Agent 的另一半
  • 反思（Reflection）、工具使用（Tool Use）、規劃（Planning） — Agent 的三種基本做事方法
  • Coding Agent 與 Work Agent — 市面上 Agent 工具的兩大類

控制工程（Harness Engineering）

來源：s4、s6 ｜ 更新：2026-11-23 ｜ Markdown 原檔

設計「告訴 AI 怎麼按步驟做事」的規範、檢查機制與工作流程。

重點

  • Harness＝告訴 AI 如何按步驟做事的機制、規範與工作流程；它的品質決定 Agent 能不能穩健完成多階段任務（s6）。
  • 頂級模型的基礎實力差距已經縮小，實際應用好壞的關鍵在 Harness（s4）。
  • Harness 包含引導 AI 做事的方法、檢查機制、工具介面；涵蓋 Prompt、RAG 與機制的設計（s4）。
  • Loop、Graph 這些流程設計，都是 Harness 的一部分（s6）。
  • 學這些名詞的目的：建立技術認知，「出外不被話術欺騙」（s6）。

例子

  • 本專案的 CLAUDE.md、檢查腳本、簡報 Graph，就是一套 Harness（s6 的簡報流程）。

常見誤區

  • 以為換更強的模型就能解決問題。s4 指出模型差距縮小，差別在 Harness。

相關概念

  • AI 代理（AI Agent） — Agent = Model + Harness
  • 提示工程（Prompt Engineering）、上下文工程（Context Engineering） — Harness 裡處理「問什麼」與「給什麼資料」的部分
  • 反思迴圈（Reflection Loop）、圖形工作流（Graph） — Harness 裡的流程控制
  • 員工手冊（AGENTS.md / CLAUDE.md） — Harness 寫成文件的樣子

提示工程（Prompt Engineering）

來源：s1、s2、s6 ｜ 更新：2026-11-23 ｜ Markdown 原檔

設計怎麼問 AI，並透過多輪討論修正，提煉出最好的產出。

重點

  • 聚焦在設計提問指令，以及和 AI 多輪反覆討論、互動修正的技巧（s6）。
  • System Prompt 放角色與規則，User Prompt 放使用者問題；RAG 會把檢索資料和問題組合進 Prompt（s1）。
  • Prompt 也要設計「找不到資料時怎麼回答」，並改成符合情境的句子（s1）。
  • AI 幫忙寫的 Prompt 常常過長，有些模型吃不下反而變差，要親自測試並精簡（s2）。
  • 簡單 Prompt 能一次解決的問題，就不需要 Loop（s6）。

例子

  • 07C 用 System Prompt 教 AI 打草稿的步驟：先確認事實 → 評估失落點 → 發想幽默切入點 → 生成正文（s2）。

常見誤區

  • 「Prompt 越長越詳細越好」——s2 提醒過長反而會壞掉。

相關概念

  • 上下文工程（Context Engineering） — 下一層：不只問得好，還要給足資料
  • 過度工程化（Over-engineering） — Prompt 能解決就不要用 Loop
  • 規劃（Planning） — 打草稿的步驟是靠 Prompt 教的

上下文工程（Context Engineering）

來源：s1、s6 ｜ 更新：2026-11-23 ｜ Markdown 原檔

把足夠而且正確的背景資料交給 AI，讓它不用亂猜。

重點

  • 聚焦在如何構建並傳遞「足夠充分且正確的背景資訊」給 AI（s6）。
  • 核心目的是避免 AI 在資訊不足時盲目猜測或產生幻覺（s6）。
  • 常見做法：傳統 RAG，以及本課程實作的 LLM Wiki（s6）。
  • RAG 把檢索到的背景資料和問題一起放進 Prompt，讓 LLM 像做「閱讀測驗」一樣作答（s1）。

例子

  • 第七週 RAG 機器人測試時要確認它「嚴格根據資料回答，而不是自行幻想」（s1）。

常見誤區

  • 只顧著改問法（Prompt），卻沒給 AI 需要的資料；資料不夠時 AI 只能猜（s6）。

相關概念

  • 提示工程（Prompt Engineering） — 上一層：怎麼問
  • 檢索增強生成（RAG）、LLM 知識庫（LLM Wiki） — 兩種提供 context 的做法
  • 控制工程（Harness Engineering） — Context Engineering 是 Harness 的一環

檢索增強生成（RAG）

來源：s1、s4、s5、s6 ｜ 更新：2026-11-23 ｜ Markdown 原檔

先從資料庫找出相關段落，再讓 LLM 根據段落回答。

重點

  • 流程：資料切塊 → 內文做 Embedding 轉向量 → 存進向量資料庫（FAISS）→ 提問時檢索 → 把段落和問題組合成 Prompt 交給 LLM（s1）。
  • 打包向量庫前，要先用測試問題驗證檢索結果是否準確（s1）。
  • 缺點一：每次提問都從原始文件重新拼湊，知識沒有累積（s5）。
  • 缺點二：向量檢索像黑盒子，找對找錯不容易看出來（s4）。
  • 中等規模的知識庫，用 index 檔就夠，不一定需要 embedding RAG（s5）。
  • 第十週把 RAG 和 LLM Wiki 並列為 Context Engineering 的常見做法（s6）。

例子

  • 第七週「勞動部工讀生權益」示範：R01 建向量庫、R02 做 Gradio 對話機器人（s1）。

常見誤區

  • 跳過打包前的檢索驗證，沒確認向量搜尋抓到的文本與 Metadata 是否準確（s1）。

相關概念

  • 上下文工程（Context Engineering） — RAG 是提供 context 的一種方式
  • LLM 知識庫（LLM Wiki） — 不需要向量、可解釋性更高的替代方案

LLM 知識庫（LLM Wiki）

來源：s4、s5、s6 ｜ 更新：2026-11-23 ｜ Markdown 原檔

讓 LLM 把原始資料整理成互相連結的 Markdown 頁面，並持續維護。

重點

  • 三層：raw（原始資料，不可修改）→ wiki（LLM 撰寫維護）→ schema（CLAUDE.md / AGENTS.md 規則）（s5）。
  • 三種操作：Ingest（吸收新資料）、Query（查詢並附引用）、Lint（健康檢查：矛盾、孤兒頁、缺頁）（s5）。
  • 和 RAG 不同：知識「編譯一次、持續更新」，交叉引用和矛盾都已整理好，會越來越豐富（s5）。
  • 不用轉向量，靠 index.md 目錄讓 Agent 直接找到頁面；人和 LLM 都看得懂，找對找錯一目瞭然（s6、s4）。
  • 建置前 AI 要先訪談：研究廣度深度、來源格式、連結風格、語言與公式規則（s6）。
  • 用 Obsidian 開啟 wiki 資料夾，Graph View 會把雙向連結畫成網絡圖（s6、s5）。

例子

  • 本專案就是一個 LLM Wiki：6 份課程資料 → 來源摘要＋概念條目 → 教學簡報。

常見誤區

  • 以為 LLM Wiki 是給人線性閱讀的文章；它主要是讓 AI 在 context 中檢索、提取（s6）。
⚠️ 來源差異：s6 說 Karpathy「最初也試圖建置傳統 RAG，後來發現…」，但 s5（Karpathy 原文）沒有提到這段經歷。本 wiki 不把這段當成 Karpathy 的說法。

相關概念

  • 檢索增強生成（RAG） — 對照組
  • 上下文工程（Context Engineering） — LLM Wiki 是提供 context 的方法
  • 員工手冊（AGENTS.md / CLAUDE.md） — LLM Wiki 的 schema 層
  • Git 版本控管（Git Version Control） — wiki 就是一個 git repo

規劃（Planning）

來源：s2、s3、s4 ｜ 更新：2026-11-23 ｜ Markdown 原檔

面對任務先拆解步驟、打草稿，再照計畫一步步完成。

重點

反思迴圈（Reflection Loop）

來源：s6 ｜ 更新：2026-11-23 ｜ Markdown 原檔

作者 Agent 產生、審查員 Agent 挑錯，反覆修訂直到合格或觸發煞車。

重點

  • 三步驟：作者 Agent 產生初版 → 審查員 Agent 依品質標準列缺點與修正建議 → 作者修訂後再送審（s6）。
  • 設計 Agent 時，重點已從寫單次 Prompt 轉向設計 Prompt Loop（s6）。
  • 成功關鍵一：客觀的放行條件，審查員才知道什麼時候可以放行（s6）。
  • 成功關鍵二：煞車機制，避免無窮迴圈和浪費 Token（s6）。
  • 流程是固定的「產生 ⇄ 審查」來回，不會跳到其他步驟（s6，與 Graph 對比）。

例子

  • 來源未提供課堂實例；本專案簡報的 N3 ⇄ R 事實審查就是一個 Reflection Loop。

常見誤區

  • 沒有分工、也沒有客觀放行條件時，審查員無從判斷何時可以放行（s6）。

相關概念

  • 反思（Reflection） — 第八週的單一 Agent 版本
  • 煞車機制（Stopping Conditions） — Loop 必備的煞車
  • 圖形工作流（Graph） — 更有彈性的流程架構
  • 控制工程（Harness Engineering） — Loop 是 Harness 的一部分

圖形工作流（Graph）

來源：s6 ｜ 更新：2026-11-23 ｜ Markdown 原檔

把流程拆成多個節點，依條件在節點之間前進、跳回或重來。

重點

  • 每個節點（Node）只專注一個獨立任務，例如 A 寫大綱、B 檢查邏輯漏洞、C 輸出評估報告（s6）。
  • 動態條件跳躍：流程不是直線；在 C 發現原始資料遺漏，可以跳回 B，甚至退回 A，補齊後再往前（s6）。
  • 和 Loop 的差別：Loop 是固定的「產生 ⇄ 審查」來回；Graph 可以在不同節點間依條件自由跳躍與回溯，彈性更高（s6）。
  • 簡報 Graph 範例：大綱 → 逐頁內容 → HTML 渲染 → 自動驗證；驗證不過就跳回逐頁內容或大綱（s6）。
  • 驗證節點檢查：圖片路徑是否斷連結、引用是否精準、版面文字是否溢出（s6）。

例子

  • s6 的四節點簡報流程；本專案在它之上加了 Wiki 檢查、大綱檢查與事實審查。

常見誤區

  • 一開始就畫複雜 Graph。s6 提醒 Loop 能解決的問題不要過度工程化（見 過度工程化（Over-engineering））。

相關概念

  • 反思迴圈（Reflection Loop） — 比 Graph 簡單的固定迴圈
  • 人類檢查點（Human Checkpoint） — Graph 中人類介入的節點
  • 煞車機制（Stopping Conditions） — 回跳也需要上限
  • 過度工程化（Over-engineering） — 什麼時候不該用 Graph

煞車機制（Stopping Conditions）

來源：s2、s6 ｜ 更新：2026-11-23 ｜ Markdown 原檔

事先規定迴圈什麼時候一定要停，避免無限重做和浪費錢。

重點

  • 最大次數限制：例如最多反覆修訂 3～5 次就強制停止（s6）。
  • 資訊不足即停：審查發現缺乏關鍵原始資料時中斷迴圈，請人類補資料（s6）。
  • 成本效益控管：防止無效的重複修訂導致 Token 費用浪費（s6）。
  • 和「客觀放行條件」搭配：一個決定何時合格，一個決定何時放棄（s6）。
  • 程式層面的防呆：預設 False 的測試開關，避免誤觸大量 API 呼叫（s2）。

例子

  • 本專案每個 Loop 最多 3 輪；wiki 和 raw 都沒有的資訊就停下來問人類（CLAUDE.md 5.2，依據 s6）。

常見誤區

  • 只設放行條件、不設上限：品質一直達不到標準時就會無窮迴圈（s6）。

相關概念

  • 反思迴圈（Reflection Loop） — 煞車用在哪裡
  • Token 成本（Token Cost） — 煞車要保護的東西
  • 人類檢查點（Human Checkpoint） — 資訊不足時把決定交還給人

人類檢查點（Human Checkpoint）

來源：s4、s5、s6 ｜ 更新：2026-11-23 ｜ Markdown 原檔

在流程中特意停下來讓人審核的關卡，越早檢查、重做成本越低。

重點

  • 簡報 Graph 中，大綱生成後是人類管理者的最佳檢查點：在大綱階段修正，可避免之後重做 HTML 的巨大成本（s6）。
  • 管理者只要掌控「大綱審核」與「最終檢查報告」兩個關卡，中間重複的生成、驗證與修改交給 Agent（s6）。
  • 員工手冊要求「先計畫後執行」：動手修改或搬檔案前，先提計畫給人審查授權（s4）。
  • Karpathy 偏好一次 ingest 一份資料並親自參與：讀摘要、檢查更新、引導重點（s5）。

例子

  • 檔案分類器：Agent 擬好 5 類分類計畫 → 管理員確認 → 才開始搬檔案（s4）。

常見誤區

  • 等到最後成品才檢查。越後面發現問題，要重做的東西越多（s6）。

相關概念

  • 圖形工作流（Graph） — 檢查點是 Graph 中的一個節點
  • 規劃（Planning） — 計畫就是最適合審的東西
  • 煞車機制（Stopping Conditions） — 資訊不足時也要交回給人

Token 成本（Token Cost）

來源：s2、s6 ｜ 更新：2026-11-23 ｜ Markdown 原檔

Agent 每多一個階段就多呼叫一次模型，用量和費用會倍數成長。

重點

  • 一般問答只呼叫一次模型；Agent 是多階段架構，每階段都呼叫，Token 呈倍數成長（s2）。
  • Groq 免費 API 容易跑到一半因額度中斷；改用較小模型可降低中斷機率；商業級應用要用付費 API（s2）。
  • 範例程式用預設 False 的測試開關，避免一執行就燒光額度（s2）。
  • Loop 要設煞車，防止無效的重複修訂浪費 Token（s6）。

例子

  • 07C 先打草稿、再生成正文，至少兩次模型呼叫（s2）。

常見誤區

  • 迴圈設計得越多輪越好——每一輪都要花錢，也可能卡在無窮迴圈（s6）。

相關概念

  • 煞車機制（Stopping Conditions） — 控制成本的煞車
  • 規劃（Planning） — 多階段架構的例子
  • 過度工程化（Over-engineering） — 流程越複雜越燒錢

過度工程化（Over-engineering）

來源：s3、s6 ｜ 更新：2026-11-23 ｜ Markdown 原檔

用不必要的複雜流程去解決簡單問題；原則是能簡單就簡單。

重點

  • 簡單 Prompt 能一次解決的問題，絕不調用 Loop（s6）。
  • 標準 Loop 能解決的問題，不要盲目堆疊複雜的 Graph 節點（s6）。
  • 好的 Agent 流程應該從人類實際處理事情的自然步驟演化而來（s6）。
  • 第八週作業也強調：重點不是做出非常複雜的系統，而是理解方法並讓它實際運作（s3）。

例子

  • 選工具的順序：Prompt → Loop → Graph，一層不夠才往下一層（s6）。

常見誤區

  • 一開始就堆疊複雜的 Graph 節點，沒先確認簡單 Prompt 或標準 Loop 是否已經足夠（s6）。

相關概念

  • 提示工程（Prompt Engineering）、反思迴圈（Reflection Loop）、圖形工作流（Graph） — 由簡到繁的三層選擇
  • Token 成本（Token Cost） — 複雜流程的代價

員工手冊（AGENTS.md / CLAUDE.md）

來源：s4、s5、s6 ｜ 更新：2026-11-23 ｜ Markdown 原檔

放在專案資料夾裡的規則檔，告訴 AI 這個專案要做什麼、怎麼做、做到什麼程度。

重點

  • 常見檔名：agent.md（通用慣例）、claude.md（Claude）、gemini.md（Gemini）；模型載入資料夾時會自動讀取（s4）。Karpathy 也舉 CLAUDE.md、AGENTS.md 為例（s5）。
  • 好的交辦四要素：成果定義、約束條件、驗收標準、先計畫後執行（s4）。
  • 在 LLM Wiki 裡它是 schema 層：讓 LLM 成為有紀律的 wiki 維護者，由人和 LLM 一起持續調整（s5）。
  • 第十週稱它為「專案憲法與員工作業手冊」，規範目錄結構（agent.md、papers/、wiki/、assets/）（s6）。

例子

  • 約束條件例子：絕對不可刪除原始檔；無法分類的放進「待確認」資料夾（s4）。

常見誤區

  • 把規則散落在對話裡；s4 指出應寫成規格書，取代散亂的對話提示詞。

相關概念

  • 控制工程（Harness Engineering） — 員工手冊是 Harness 的書面形式
  • LLM 知識庫（LLM Wiki） — schema 層
  • 技能包（Agent Skills） — 手冊寫原則，Skill 寫具體 SOP

技能包（Agent Skills）

來源：s4 ｜ 更新：2026-11-23 ｜ Markdown 原檔

把試出來的好流程打包成可重複呼叫的 SOP，讓產出品質穩定。

重點

  • 和 AI 討論、實驗出好的工作流程後，請 AI 把 SOP 打包成 Skill（s4）。
  • Skill 可以在同一個專案或跨專案反覆調用（s4）。
  • 目的：產出的品質與風格不會每次隨機波動（s4）。

例子

  • 講師把「日系手帳風 HTML 簡報」的生成方法打包成 Skill，之後每次做簡報都照同一套規範（s4）。

常見誤區

  • 每次都重新口頭描述需求，導致每次產出風格都不一樣（s4）。

相關概念

  • 員工手冊（AGENTS.md / CLAUDE.md） — 手冊與 Skill 的分工
  • 控制工程（Harness Engineering） — Skill 也是 Harness 的一部分

Coding Agent 與 Work Agent

來源：s4、s6 ｜ 更新：2026-11-23 ｜ Markdown 原檔

Work Agent 在對話框工作，Coding Agent 能操作專案資料夾。

重點

  • Work Agent：ChatGPT / Claude 標準對話介面、CoWork、OpenWorker；不能直接讀寫本機資料夾，沒有原生版本控管（s6）。
  • Coding Agent：Google AntiGravity、Claude Code、ChatGPT Codex；綁定專案資料夾，可直接讀寫檔案，整合 Git（s6）。
  • Coding Agent 的本質不只是寫程式，而是模仿人類操作電腦專案資料夾（s6）。
  • 指令只是快捷鍵，不用背，直接用口語交代需求即可（s6）。
  • 需要斷線安全與資料隱私時，可用 OpenWorker + Ollama 跑本地小模型，但表現仍不如頂級雲端模型（s4）。

例子

  • 建 LLM Wiki、自動產生網頁簡報這類任務適合 Coding Agent（s6）。

常見誤區

  • 看到 "Coding" 就以為只能寫程式（s6）。

相關概念

  • AI 代理（AI Agent） — 兩者都是 Agent
  • Git 版本控管（Git Version Control） — Coding Agent 的優勢之一
  • 工具使用（Tool Use） — 專案資料夾就是 Coding Agent 的工具

Git 版本控管（Git Version Control）

來源：s5、s6 ｜ 更新：2026-11-23 ｜ Markdown 原檔

在本機記錄專案每一版的變化，AI 改壞了可以隨時退回。

重點

  • Git 是本機的專案歷程追蹤與版本復原；GitHub 是把本機專案推上去的雲端平台（s6）。
  • AI 在多輪 HTML 渲染中搞砸檔案時，可以用 Git 復原到之前的好版本（s6）。
  • LLM Wiki 本身就是一個 Markdown 的 git repo，免費得到版本歷史、分支與協作（s5）。

例子

  • 本專案以 git init 建立，完成後推上 GitHub Pages。

常見誤區

  • 把 Git 和 GitHub 當成同一個東西（s6）。

相關概念

  • Coding Agent 與 Work Agent — Coding Agent 深度整合 Git
  • LLM 知識庫（LLM Wiki） — wiki 就是 git repo
